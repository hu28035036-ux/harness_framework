# Architecture Decision Records

## 철학
빠른 MVP를 우선하되, 녹화 엔진, PC 앱 셸, DB, 파일 스토리지는 계약 뒤에 숨겨 추후 교체 비용을 낮춘다.

---

### ADR-001: Next.js + TypeScript strict 선택
**결정**: 웹과 API는 Next.js 15 App Router와 TypeScript strict mode로 구현한다.  
**이유**: 웹 화면과 API를 한 저장소에서 빠르게 개발할 수 있고, 타입 계약을 공유하기 쉽다.  
**트레이드오프**: 초기에는 서버와 웹 배포가 강하게 묶인다.

### ADR-002: Electron 기반 PC MVP
**결정**: PC 프로그램 MVP는 Electron으로 구현한다.  
**이유**: TypeScript 코드와 UI 컴포넌트 재사용이 가능해 초기 속도가 빠르다.  
**트레이드오프**: 배포 크기가 커질 수 있으므로 녹화/저장/업로드 로직은 Electron에 종속시키지 않는다.

### ADR-003: RecorderBackend 분리
**결정**: FFmpeg는 `RecorderBackend` 구현체 중 하나로 둔다.  
**이유**: GraphicsCaptureRecorder 또는 네이티브 캡처로 교체할 때 상위 작업 흐름을 바꾸지 않기 위해서다.  
**트레이드오프**: 초기 인터페이스 설계와 테스트 더블이 필요하다.

### ADR-004: 로컬 우선 저장과 업로드 큐
**결정**: 캡처/클립은 항상 로컬 저장 후 업로드한다.  
**이유**: 네트워크 장애, 강제 업데이트, 앱 재시작에도 작업 인증 자료를 복구해야 한다.  
**트레이드오프**: 로컬 상태 파일의 무결성 관리와 복구 테스트가 필요하다.

### ADR-005: 서버 정책 검증
**결정**: 권한, 홍보글 10분 제한, 게시 가능 상태, 평점 토큰은 서버에서 검증한다.  
**이유**: UI 제한만으로는 정책 우회가 가능하다.  
**트레이드오프**: API 테스트가 MVP 초반부터 필요하다.
